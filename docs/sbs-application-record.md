# SBS application record (CV2P-77 / PSC-88)

Organisation sponsorship creation opens the editable SBS record at `/applications/{id}`. The two cards follow the ticket reference: Summary and Sponsorship. The generated SBS ID, sponsor type and linked organisation are read-only; status, priority, critical date, counsellors and migration agent save together with sponsorship milestones and outcome/appeal fields. Notes use the existing separate notes editor.

Counsellor 1 defaults to the creator. Creation uses the first SBS workflow by ID, when configured, and its migration agent. SBS records can be reassigned to any active, unrestricted staff member with a configurable staff role. Counsellor 1 and Migration Agent are mandatory on the record form. Workflow administration remains the existing `ApplicationWorkflow` model integration; this ticket does not add a workflow administration screen.

The four persisted milestones default to `To do`: initial consultation, service agreement, supporting documents and application. Transitioning Application to `Lodged` sets Status to `Pending Decision` and Outcome to `Awaiting decision`; saving an already-lodged record preserves later decisions. Saving an agreement activity with status `Sent` / `Sent - Pending Client`, or `Signed` / `Digitally signed`, updates the service-agreement milestone. The existing Agreements activity model is the integration point; the repository has no external sending or digital-signature provider.

TRN is optional except when activating the SBS, and must contain exactly 13 ASCII alphanumeric characters when supplied. Final outcomes require an outcome date. Outcome `Refused` shows the appeal block; `Not reviewable` requires a blank appeal deadline. An appeal final outcome requires its date. Approval through either the original outcome or an appeal requires an expiry date on or after the effective outcome date. The organisation table's approval date mirrors that effective date. The migration carries existing SBS approval dates into the new outcome fields without changing Labour Agreements.

Only one SBS per organisation can be Active. The save transaction locks the organisation before the application and checks every SBS for that organisation, including records assigned to other staff. Labour Agreements have their own independent one-active-record rule (CV2P-171). Sponsor type cannot be changed after creation, including through the older detail editor. Activating a replacement requires the existing sponsorship of that type to expire or leave Active first.

Sponsorship expiry is inclusive: on its expiry date, the persisted status becomes `Expired`. `php artisan sbs:expire` handles both SBS and Labour Agreements, is idempotent and scheduled every minute. Authenticated CRM requests also catch up due records, so lists, records and nomination defaults agree between scheduled runs. Dates follow the application's configured timezone. Run Laravel's scheduler (`schedule:run` every minute or `schedule:work`) for unattended expiry processing.

Default SBS and Labour Agreement tabs are Tasks, RFI, Nominations, Payments and Agreements. Configuration > Application Types can change the enabled tabs through the shared SBS category, including disabling them all or retaining Quotes. The Nominations tab comes after RFI and displays only assigned nominations in the same organisation whose `sponsorship_id` references this sponsorship. It shows linked Nomination ID, full nominee name, visa subclass/pathway and status, with pagination. It has no create/link actions; sponsorship is selected on the nomination record.

Deploy with `php artisan migrate` and `npm run build`. `SbsRecordTest` covers the form, workflow defaults, reassignment, persistence/rollback, lodgement, active-SBS conflicts across staff, TRN/staff validation, appeal dates, expiry boundaries/idempotency, scoped nominations, agreement events and immutable sponsor type. Related application, sponsorship, organisation, nomination, tab and link tests cover integration with existing flows.
