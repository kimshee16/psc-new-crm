# Applications list (PSC-12)

`/applications` lists persisted applications assigned to the authenticated user by primary counsellor, secondary counsellor, or migration agent user ID. This assignment scope also applies to administrators, CSV exports, and viewing/updating the record at `/applications/{id}`. The list/export exclude finalised and withdrawn statuses (case-insensitive, trimmed). Assigned closed records remain accessible at their record URL.

Run `php artisan migrate` and `npm run build` when deploying. This adds application and summary support without generating illustrative records. The Create Application modal (PSC-33) creates applications or leads from Client and linked Lead records. Summary editing is available on persisted application records.

The application ID is the table's numeric primary key. `client_id` references `clients.id`; the three staff foreign keys reference `users.id`. Category-specific fields are `course`, `visa_subclass` (full subclass label), `nomination_pathway` (full pathway name), and `assessment_body`. Citizenship and SBS use fixed descriptions, and blank study courses display “Course TBD”. Priority is H, M, or L.

Filters, sorting, and pagination run on the server. Filters are combined with AND; selected priorities use OR. Text searches are case-insensitive literal substrings. Date ranges are inclusive. Blank dates sort last in both directions; other sort ties use descending ID. Download CSV applies the form's current filters and sort to all matching records, independent of page size. CSV has UTF-8 BOM and guards against spreadsheet formula injection.

## Application Summary (PSC-29)

`resources/views/components/applications/summary.blade.php` is the reusable Summary card at the top left of the record. It provides a linked client or organisation name, generated Application ID, full application type label, conditional fields, editable status/priority/date/staff, system timestamps, and an accessible native notes dialog. Done keeps a notes draft; Save summary persists it. Cancel/Escape in the dialog discards that dialog's changes. Notes are plain text (up to 60,000 characters), escaped when rendered. Dates display in the configured application timezone, shown on Last Modified.

`PATCH /applications/{application}` accepts only Summary edits and enforces assignment access, field requirements, workflow choices and eligible staff on the server. Owner, ID, type, workflow and timestamps cannot be changed. Visa Subclass and Assessment are editable and mandatory for their types. PSC Client and Nomination subclass have blank editability cells in the supplied requirement; they are treated as read-only after creation pending clarification. Notes are optional and editable. Migration Agent is mandatory only for Visa. Reassigning all of the current user's roles redirects to the list because the user no longer has record access.

New `ApplicationWorkflow` records hold `summary_options` keyed by `visa_subclass`, `assessment_body`, and `nomination_pathway`, each containing an array of string values. These persisted workflow choices override the corresponding PSC-33 creation catalogue when configured. `migration_agent_id` supplies the default agent. Its `caseHandlers()` relationship grants staff case-handling permission. For a workflow, eligible assignees are these staff, existing case assignees, and the workflow agent; all must have an active, unrestricted portal account with a configured staff role. Legacy applications without a workflow use active, unrestricted staff roles. No workflow administration screen existed in this repository; these model interfaces are the integration points for workflow configuration.

The existing choice is retained if removed from workflow options so an older case can still be saved. Other cases cannot select retired values. Missing options are shown with an administrator message. New `Organisation` records provide a real, assignment-scoped linked record showing its assigned applications; organisation applications also appear in the existing list and CSV under the owner-name column.

`ApplicationSummary::create($creator, $attributes)` is the shared creation boundary for PSC-33. It requires exactly one existing client/organisation, a supported type and its mandatory conditional value, checks workflow/type compatibility, and defaults status to Not Started, priority to M (Medium), Counsellor 1 to the creator, and Migration Agent to the workflow's agent. It preserves supplied selections; ART Appeal accepts both true and false for PSC Client. The PSC-33 creation flow uses this service. Eloquent creation also supplies status/priority and authenticated creator/workflow-agent defaults, but does not replace the service's validation. Existing imported records are not rewritten or retroactively assigned defaults.

The schema retains legacy SBS applications, adds ART Appeal, and permits organisation ownership without a client. Rollback refuses to remove the schema while organisation-only applications or ART appeals exist, avoiding loss of ownership/type information.

Validation: `php artisan test --filter=ApplicationSummaryTest` covers all six types, linked records, defaults, creation validation, editing and optional-field clearing, timestamps, escaped notes, immutable fields, required values, eligible staff, workflow choices, access and reassignment. Run the complete suite with `php artisan test`.

## Create Application (PSC-33)

Client and linked Lead records now share `components/applications/create-modal.blade.php`. It opens a native dialog with keyboard focus containment, Escape/Cancel, searchable choices, conditional required fields, validation messages, and restored selections after a failed submission. Application Type starts blank. Individual services are Study and 500 Visa, Study, Visa, Assessment, ART Appeal, and Citizenship; organisation services are excluded.

`POST /clients/{clientId}/applications` creates applications for the source client. Its existing PSC-38 Lead-only payload remains compatible. `POST /leads/{leadId}/applications` uses the same office/assignee access scope as the Lead record, derives client ownership from that Lead, and converts it only after successful application creation. Client IDs in these URLs are public client IDs, while application ownership and `source_lead_id` use database primary keys. Submitted owner and staff overrides cannot replace the source client or creator.

`ApplicationCreation` orchestrates the existing `ApplicationSummary` creation boundary. Combined creation writes two distinct IDs, presets the Visa subclass to `500 - Student Visa`, links each record to the other through `linked_application_id`, and redirects to Study. Both writes, reciprocal links, and Lead conversion share a transaction. Failed Visa creation leaves no Study record or converted Lead. The source Lead is locked during conversion; a repeated submission returns its existing application without making duplicates, subject to application access.

Workflow templates come from `ApplicationWorkflow`, filtered by type. If templates exist for a type, a selection is required; otherwise the service uses its standard type fields. Combined creation offers separate Study and Visa templates, with Visa choices restricted to templates accepting subclass 500. Workflow `summary_options` override the corresponding catalogue in `config/applications.php`; omitted keys inherit the documented catalogue. The two 485 variants are distinct full-label values. No workflow configuration screen or additional workflow stages are invented here; CV2P-83 was inaccessible, so its future configuration implementation should populate the existing model.

Visa and ART Appeal require a subclass. ART Appeal also requires PSC Client and accepts both Yes and No. Assessment body is optional at creation as specified in PSC-33, although the PSC-29 Summary editor still requires it when saving a summary. Visa records retain the existing mandatory Migration Agent rule: the template agent is used when configured, otherwise the modal asks for an eligible agent. All application records default to Not Started, Medium, and the creating user as Counsellor 1.

The confirmed Lead-only behavior creates a Lead from a Client, or keeps an existing Lead unchanged, without applications or conversion. Conditional application fields and workflow selection do not apply in this mode. Active assigned applications now appear alongside active leads on the Client record. Linked application navigation is assignment scoped on both sides.

Browser smoke checks cover blank defaults, combined template selection/default agent, ART conditional fields, subclass search, Lead-only toggling, and Cancel.
